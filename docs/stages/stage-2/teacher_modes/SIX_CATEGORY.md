**Conditions on the three proposed sources.**
- **Toucan.**
  - Admit only rows whose recorded generator (`metadata.synthetic_data_gen_configs`) is on the permissive
    allowlist.
  - Keep the Apache-2.0 notice.
  - The tool responses are third-party web content that may carry residual PII. Generations over them stay
    outside git (P15).
  - It has no gold arguments: its calls are checked by schema and by agreement with the recorded trajectory.
  - Its card and paper disagree on whether failed tool calls were filtered.
  - Download only the configs the pool reads (P8.4).
- **The two Pivot sets.**
  - Each row is one step behind an expert-written prefix. Read as is, the teacher would continue another model's
    assistant turns, which is a P17 problem.
  - **Proposed instead:** rebuild each trajectory from its step rows, let the teacher run from the first step, and
    replay the recorded tool response only when its call equals the step's `expected_action` (exact after
    canonicalization). Foreign assistant turns never enter the context.
  - Attribution is required, and the sets must be decontaminated against the benchmarks (their seeds are unnamed).
  - The cards' row counts disagree with the Hub's.
- **WorkBench.**
  - Generate new instances from its templates; never use its 690 published tasks.
  - It is never reported as held-out evaluation, because its task families are shared with the benchmark.

**Verification classes, reported apart.**
- **G1:** the task's own program defines the answer (WorkBench's final database state).
- **G2:** model-generated gold compared deterministically (Pivot's expert actions; Toucan's target tools and
  recorded calls). This is agreement with another model's filtered trajectory, not human-verified correctness.
- **B:** behavioural, no call where none is wanted.

**Gaps with no legal deterministic source** (each a SHORTFALL risk; never filled from another category):
- parallel calls with gold arguments (only xLAM had them);
- "ask for the missing parameter" (only When2Call train, xLAM-derived);
- an MCP success check beyond recorded-trajectory agreement (Toucan has no final state).

## 2. The canonical tool-calling task pool (`tool_pool@v1`)

One versioned pool serves all three lineages: the hybrid in thinking mode (A1-6cat), the hybrid in non-thinking
mode (A2-6cat) and Thinking-2507 (C1-6cat). Its own splits also serve a future search's state evaluation and
calibration. Every teacher receives the same task ids in the same order.

**A task** (`six_category_design.json :: task_pool.task_record`) holds:
- **inputs:** the tool schemas (JSON Schema, canonicalized), the user turns, and the system text the source carries;
- **backend:** a deterministic tool backend. Either a replay table (canonical call → recorded response) or an
  executable implementation (pinned code, no network) run inside the episode loop. Never a live API, a network
  call, or a tool simulated by an LLM at generation time;
- **success criterion:** each step's gold call set (with the argument variants the task allows) or the sandbox's
  final state, and a final check.

Upstream assistant turns are never kept as targets.

**Seven categories** (shares in supervised tokens, proposed for the maintainer to confirm):

| category | covers | share | proposed sources (verification class) |
| --- | --- | ---: | --- |
| tool selection | the right function among the offered tools, its name, simple arguments, one call | 15% | WorkBench (G1), Pivot (G2), Toucan (G2) |
| schema and arguments | one call with nested objects, arrays, enums, units or optional fields | 15% | WorkBench (G1), Pivot (G2); JSON Schema always |
| no tool needed | tools offered, none needed or none fits: answer directly | 10% | Toucan irrelevance, Pivot chat steps (B) |
| multiple and parallel calls | two or more calls, in one turn or in sequence | 15% | WorkBench sequential (G1); Toucan parallel by names and replay only (G2); gold parallel arguments: none |
| multi-turn | sequential calls, reading tool results, follow-up reasoning, final answer from the results | 20% | WorkBench (G1), Pivot conversational (G2), Toucan (G2) |
| errors and missing parameters | tool errors and failures; a required value missing | 10% | WorkBench tool errors (G1, partial); missing parameter: none admitted |
| MCP / agent | MCP-server tool catalogs, multi-step agent tasks | 15% | Toucan only (G2: target tools, order, replay; no final state) |

Verification strength is reported per category. A category without a legal, deterministic source is a SHORTFALL in
every arm. It is never filled from another category.

**Splits by atomic tool identity, not by task** (revised 2026-11-03 after the maintainer's review; see
[`PACKED_ROUND.md`](PACKED_ROUND.md) section 5).
- An atom is every MCP server a task's converter declares, and every tool no declared server owns (its bare name and
  schema). Each atom is assigned by `sha256('tool_pool@v1|' + atom) mod 100`: 3% validation, 4% state evaluation, 4%
  calibration, 2% reserve, 87% training. A task enters the split all its atoms share, and is refused when they
  disagree.
- So no server or tool appears in two splits. This is the tool-calling counterpart of P10.2's held-out families. The
  first version hashed a task's servers joined into one string, which could put one server in two splits.
- The training split's order is a seeded shuffle (seed 20261103), frozen with its sha256 before any generation.

**Isolation** (T1–T5 in the design):
- T1: eval-set-1's held-out items, including its 12 tool prompts (5 Glaive in the formal core, 7 xLAM withheld),
  share no content key or tool family with the pool (`shared.eval_sets.require_disjoint`).
- T2: no benchmark's evaluation data (BFCL, API-Bank, ToolBench test, τ-bench, When2Call test) enters the pool.
- T3: no Glaive or xLAM row, and no task that duplicates one, including through a dataset that repackages them.
- T4: the splits are disjoint by atom and content key, and a 13-gram near-duplicate of an earlier split's task is
  refused.
- T5: exact and normalized-query duplicates collapse to one task.

**Length.** A task whose first rendered prompt exceeds 6,144 tokens under any of the three templates is left out for
every teacher, and the exclusion is recorded. Every turn then keeps at least 2,040 tokens of generation allowance
inside the 8,192-token training sequence, so nothing is ever cut.

**Size needed.** A2-6cat walks the longest prefix of the order: about 2,300–6,900 admitted tasks, so 3,500–15,000
training tasks at pass rates of 0.45–0.8. A smaller legal supply is reported as a SHORTFALL per category.

## 3. Teacher-native generation, tool execution and verification

Each teacher uses its own official template and sampling preset. The tools are passed through
`apply_chat_template(tools=...)`, and nothing is prefilled by hand.

| | A1-6cat | A2-6cat | C1-6cat |
| --- | --- | --- | --- |
| teacher | `Qwen/Qwen3-4B@1cfa9a72` | the same | `Qwen/Qwen3-4B-Thinking-2507@768f209d` |
| mode | thinking (`enable_thinking=True`) | non-thinking (`enable_thinking=False`, preclosed think) | thinking: its template opens `<think>` |
| sampling | T 0.6, top-p 0.95, top-k 20 | T 0.7, top-p 0.8, top-k 20 | T 0.6, top-p 0.95, top-k 20 |

**Execution.** The runner is `run_battery.run_episodes`' episode loop, the one interactive episodes already use.
- Each turn's prompt is the template's rendering of the conversation so far. The tool backend answers the turn's
  parsed calls with tool messages.
- An episode ends at a turn without a call, at the task's turn limit, or at any non-EOS stop.
- Allowance per turn: 8,184 minus the rendered prompt. A turn that reaches it is training-length-limited, and its
  episode is refused whole.
- Seeds come from `request_seed(seed_base, task_id, turn)`, with candidate pass k at `seed_base + k`. The rule is the
  same for every teacher, so the seed depends on the task and the turn, not the model.
- Two candidates: the second only for a task whose first candidate fails verification.
- The next turn's context renders the parsed assistant turn through the template, as a deployed runtime does.
  Whether that re-rendering reproduces the generated ids is recorded per turn. Only generated ids are ever
  supervised.

Implementation owed before any paid run:
- passing `tools` and tool messages through that loop;
- the backend adapter;
- the verifier.

These are small, and they wait for the source ruling because the backend depends on the sources.

**Verification** runs on the dev box: one pure-Python verifier for every teacher, with no teacher-specific leniency.
1. **Protocol.** Natural termination, no degeneration stop, and the mode's think state (closed before any call in
   thinking mode, the preclosed empty think in non-thinking mode). Every `<tool_call>` block is JSON with a name and
   arguments.
2. **Schema.** An offered tool; the arguments validate against its JSON Schema.
3. **Gold.** Each step's call set equals the gold set, order-free for parallel calls (G2). For an executable task,
   the final state equals the ground truth (G1).
4. **Execution.** The backend answered every call. An off-script call ends the episode, which is refused and counted
   per teacher. This is a selection effect, and it is reported.
5. **Task success.** The final turn makes no call and passes the task's final check.

An episode enters training whole, and only if checks 1–5 pass on every turn.

**Supervision.**
- Only the teacher's own assistant output ids are supervised (CE and KD at the target positions).
- System text, tool schemas, user turns and tool responses are context, never targets.
- No arm ever reads another teacher's or mode's output ids, thinking, tool calls or reference logits, nor the
  upstream dataset's assistant turns.

**Records.** Per turn: the task id, teacher revision, mode, template and tokenizer sha256, seed, prompt and output
token ids, raw text, parsed calls, backend responses, stop reason and scored positions. Per episode: every check's
verdict, the source, family and category. Shards are sealed with sha256.

**The pairing report** gives, per category and source:
- the tasks offered and the tasks each lineage admitted;
- the intersections: A1-6cat with C1-6cat, A1-6cat with A2-6cat, and all three;
- refusals by check;
- the family distribution and the supervised-token deviation from the quota.

## 6. Packs, token quotas, optimizer steps and budget: the method

**Steps:** T = ceil(3 × training sequences / 2) at batch size 2 over 3 epochs.
- Warmup is max(10, round(0.05 T)), evaluation every max(25, T // 8), saves every max(200, T // 2).
- None of the historical 2,468 sequences or 3,702 steps is carried over as a fact.

**Sequences.**
- C1-6cat: 989 kept plus the new tool sequences. E1's packer opens a sequence per system-prompt group, and a tool
  task's tools sit in its system prompt, so this is about one sequence per conversation unless tasks share a catalog.
- A1-6cat and A2-6cat: the rebuilt pack's own count. The estimate is non-padding tokens / (8,192 × (1 − the current
  pack's padding share)).

**Per unit:** hours = T × seconds per step, plus:
- in-training evaluation and saves: 100 / 320 / 640 s;
- the formal evaluation: 2,653 / 3,198–3,917 / 7,834 s;
- fixed time: 300 / 600 / 1,200 s.

Cost is the hours × $1.11/h (L40S $1.09 plus container disk). Seconds per step are measured figures:
- A1-6cat: A1's 6.18–6.20;
- A2-6cat: 5.66, from the L40S check;
- C1-6cat: D4-Augmented's 3.6 on the same packer (`plans/budget_v2.json`).

**Estimates** (lower / expected / upper, per seed; one variable each):
- A1-6cat: non-padding per tool supervised token of 2 / 4 / 6.
- A2-6cat: context and supervised tokens per tool turn of 400+120 / 900+70 / 1,500+40.
- C1-6cat: 500 / 1,000 / 1,600 new tool sequences.

**What each pair can say, and what stays unmatched.**
1. **Historical D4-Augmented vs C1-6cat.** Tool data, KD method, step count and data order all change together. The
   difference cannot be attributed to target-position Top-200 KD alone.
2. **C1-6cat vs A1-6cat.** An end-to-end cross-lineage comparison. Matched: the tool task pool, its categories and
   its verifier. Unmatched: teacher, initialization (and the state evaluation that selected it), the five other base
   types (sources, verification, cut traces), the fluid subdivision and its rendering, packing, and steps. It is
   never presented as a teacher-only contrast.
3. **A1-6cat vs A2-6cat.** The mode comparison. Same recipe, same pool and Top-1, each mode's own native outputs.
   Token-matched, not step- or FLOPs-matched: A2-6cat carries several times A1-6cat's non-padding tokens.
4. **A1 (done) vs A1-6cat.** The mixture comparison. Same teacher, Top-1, fluid data and base-category total.
   Tool calling enters at 1/6, and each other type drops from 1/5 to 1/6. The pack and step count differ.
5. **Original C1** (D4-Augmented's pack + Top-200): superseded by the brief, never run, never compared.

**Measurement limit.** eval-set-1 measures tool calling with 5 formal-core prompts (`eval_behavior_v0`). Fluid
reasoning (570 static and 144 interactive items) and the other units are measured as before. So the six-type data's
effect on tool calling itself can hardly be measured on eval-set-1. A tool-calling unit would be a new registered
set (eval-set-2), a maintainer decision under P10.3. It could come from the pool's held-out families, and from BFCL
under its own contract.

  set v2. A Thinking-2507 search gets a new suite built the same way. v1 and `state_eval@v1` stay frozen, and
